# 提示词优化方案

## 一、现状分析

### 当前提示词定义位置
- 文件：`dingRing-common/src/main/java/com/dingring/common/constant/PromptConstants.java`
- 共 8 个提示词常量，被 5 个模块引用

### 下游依赖关系（改提示词不能破坏的契约）

| 提示词 | 下游检测逻辑 | 测试断言（必须保留的关键词） |
|---|---|---|
| `CHAT_BASE` | `ContextBuilder.buildSystemPrompt()` 用 `String.format` 注入 agentName | `"你的花名是「老王」"`（ContextBuilderTest L163） |
| `GROUP_MEMBERS_HEADER` | `ContextBuilder.buildMemberRoster()` 前置 | `"群成员名单"`（ContextBuilderTest L178） |
| `COLLABORATION_PROTOCOL` | `DiscussionEngine.speakOnce()` 检测 `[[CONCLUDE]]` / `[[PASS]]` | `ContextBuilder.CONCLUDE_MARKER` / `PASS_MARKER` 常量不变 |
| `CONCLUSION_STAR` | `ContextBuilder.buildForConclusion()` + `ChatOrchestrator.generateConclusion()` | `"STAR 框架"`（ContextBuilderTest L224）、MockLlmService 检测 `"STAR"` 关键字 |
| `USER_PROFILE_EXTRACT` | `SimpleProfileService.extractAndMerge()` 只做 `.trim()`，不解析格式 | 无格式断言 |
| `INTENT_CLASSIFIER` | `MessageRouter.route()` 解析 JSON | MessageRouterTest 用 mock LLM，不依赖提示词内容 |
| `HOST_DECISION` | `ModeratorService.decide()` 解析 JSON | ModeratorServiceTest 用 mock LLM |
| `KNOWLEDGE_EXTRACT` | `CardEventHandler` 解析 JSON 数组 | 无提示词断言 |

### 核心约束
1. `CHAT_BASE` 中的 `你的花名是「%s」` 格式必须保留（测试断言依赖）
2. `CONCLUSION_STAR` 中的 `STAR 框架` 关键词必须保留
3. `GROUP_MEMBERS_HEADER` 中的 `群成员名单` 关键词必须保留
4. `CONCLUDE_MARKER` / `PASS_MARKER` 常量值不变，仅优化提示词中的描述

## 二、优化方案（5 项，按优先级排序）

### 优化 1：CHAT_BASE — 加发言长度和格式约束（P0）

**问题**：当前没有限制输出长度，LLM 每次输出 500-800 字，浪费 token 且不像真实群聊。

**方案对比**：

| 方案 | 描述 | 优点 | 缺点 |
|---|---|---|---|
| A. 硬限制 | "3-5 句话，100-200 字" | token 节省最显著，群聊节奏最自然 | 技术深度讨论时可能太短 |
| B. 软限制 | "保持简洁，不超过 300 字" | 留有余地 | LLM 对"简洁"理解不一致，效果差 |
| C. 不改 | 维持现状 | 零风险 | 持续浪费 token |

**选择方案 A，理由**：
- 从日志看，glm-5.2 单次发言 500-800 字，占 token 消耗 74%，限制到 100-200 字可节省 ~60% token
- 群聊场景天然是短消息交互，不是长篇独白
- "3-5 句话"用句子计数而非字符计数，LLM 遵循度更高（字符数 LLM 无法精确控制）
- 技术讨论中 3-5 句话足以表达一个观点，过长的发言反而打断讨论节奏

**Tradeoff**：牺牲了偶尔需要的深度分析（可以用 @提及触发 Agent 多轮深入），换取整体讨论效率和成本控制。

**改动**：
```java
// PromptConstants.java CHAT_BASE
public static final String CHAT_BASE = """
        你正在参与一个多人群聊讨论，你的花名是「%s」。历史消息以「花名: 内容」形式给出。
        发言要求：
        - 直接输出你的发言内容，不要重复花名前缀
        - 每次发言 3-5 句话（约 100-200 字），像真实群聊一样简短聚焦
        - 可用 Markdown 加粗、列表等基本格式，但不要用标题（#）
        - 与前面的讨论自然衔接，不要重复已有观点""";
```

**测试影响**：`"你的花名是「老王」"` 仍保留，ContextBuilderTest 不受影响。

### 优化 2：COLLABORATION_PROTOCOL — 加 few-shot 示例（P1）

**问题**：`[[CONCLUDE]]` 和 `[[PASS]]` 标记有时被 LLM 篡改（大小写不一致、位置错误、加了多余文字）。

**方案对比**：

| 方案 | 描述 | 优点 | 缺点 |
|---|---|---|---|
| A. 加示例 | 在描述后附 few-shot 示例 | 格式遵循度最高（few-shot > 纯描述） | 增加约 50 token |
| B. 加强调 | 只加"严格""精确"等强调词 | 不增加长度 | 效果远不如示例 |
| C. 不改 | 维持现状 | 零风险 | 标记格式偏差持续存在 |

**选择方案 A，理由**：
- 标记检测失败会导致整轮讨论无效（CONCLUDE 没被检测到 → 讨论不收束 → 继续浪费 LLM 调用）
- few-shot 示例对格式遵循的提升效果远超纯文字描述（业界共识：examples > instructions）
- 50 token 的系统提示开销 vs 一轮无效讨论的 1000+ token 浪费，ROI 极高

**Tradeoff**：系统提示稍长（+50 token），但每次讨论 5-10 轮调用中只要避免 1 次标记失败就回本。

**改动**：
```java
// PromptConstants.java COLLABORATION_PROTOCOL
public static final String COLLABORATION_PROTOCOL = """
        协作协议（严格遵守）：

        1. 认为讨论已充分、可以总结时，在发言末尾另起一行，精确输出标记 [[CONCLUDE]]
           示例：
           我觉得可以收尾了。
           [[CONCLUDE]]
           其他情况绝不要输出或提及该标记。

        2. 对当前讨论没有新观点时，只输出 [[PASS]]，不输出任何其他内容
           示例：[[PASS]]
           有实质内容时绝不要输出该标记。不要为了发言而发言。""";
```

**测试影响**：`CONCLUDE_MARKER` / `PASS_MARKER` 常量值不变，DiscussionEngineTest、StreamMarkerGuardTest 不受影响。

### 优化 3：CONCLUSION_STAR — 加结构模板和长度限制（P1）

**问题**：结论格式不统一（有时用 `##`，有时用 `###`，有时纯文本），长度不可控（500-1500 字），前端 HTML 渲染效果不一致。

**方案对比**：

| 方案 | 描述 | 优点 | 缺点 |
|---|---|---|---|
| A. 完整模板 | 给出 `##` 标题 + 每段内容要求 + 500 字限制 | 输出一致，HTML 渲染美观 | 结构较固定 |
| B. 轻量约束 | 只加"用 ## 标题"和"500 字以内" | 改动小 | 仍不够具体 |
| C. 不改 | 维持现状 | 零风险 | 格式随机 |

**选择方案 A，理由**：
- 前端刚加了 HTML 渲染支持（`renderMarkdown` + `dangerouslySetInnerHTML`），统一的 `##` 标题能让渲染效果最佳
- STAR 框架本身就是 4 段结构，给模板只是把隐式期望显式化
- 500 字限制可控制结论生成成本（当前有时 1500 字）

**Tradeoff**：牺牲了 LLM 的结构自由度，但 STAR 框架本身就是固定结构，自由度带来的价值很低。

**改动**：
```java
// PromptConstants.java CONCLUSION_STAR
public static final String CONCLUSION_STAR = """
        你被推选为本次群讨论的总结者。请针对主题「%s」，基于完整讨论记录，用 STAR 框架输出 Markdown 格式的讨论结论。

        格式要求：
        ## Situation（背景）
        一段话概述讨论的起因和背景。

        ## Task（任务）
        讨论要解决的核心问题。

        ## Action（行动）
        用列表归纳各方观点（标注发言人花名）：
        - **花名**：观点摘要
        - **花名**：观点摘要

        ## Result（结论）
        达成的共识、未解决的分歧、后续建议。

        全文控制在 500 字以内。""";
```

**测试影响**：`"STAR 框架"` 关键词仍保留，ContextBuilderTest L224 不受影响。MockLlmService 检测的 `"STAR"` 关键字也保留。

### 优化 4：USER_PROFILE_EXTRACT — 加格式示例（P2）

**问题**：当前描述"纯文本，每行一条，以 - 开头"有歧义——LLM 有时输出 `- 要点`（Markdown 列表），有时 `-要点`（无空格），影响后续解析。

**方案对比**：

| 方案 | 描述 | 优点 | 缺点 |
|---|---|---|---|
| A. 加格式示例 | 附 2 行示例锚定格式 | 解析零歧义 | 增加约 30 token |
| B. 不改 | 维持现状 | 零风险 | 偶尔格式不一致 |

**选择方案 A，理由**：
- `SimpleProfileService` 直接把 LLM 输出 `trim()` 后存入 `profileText`，不解析格式
- 但 `profileText` 会在后续作为"已有画像"传给 LLM，格式不一致会扰动 LLM 的理解
- 30 token 的开销可忽略

**Tradeoff**：无显著缺点。

**改动**：
```java
// PromptConstants.java USER_PROFILE_EXTRACT
public static final String USER_PROFILE_EXTRACT = """
        你是用户画像分析师。请基于「已有画像」与「最近一段群聊对话」，输出更新后的用户画像。
        关注用户的表达习惯、情绪基调、决策偏好、思考方式等长期稳定特征。
        画像是跨群的全局特征，不要把特定群的讨论话题当作用户的长期特征。

        严格按以下格式输出 3-6 条，不要输出任何其他内容：
        - 第一条特征描述
        - 第二条特征描述
        - ...""";
```

**测试影响**：无测试断言格式，不受影响。

### 优化 5：INTENT_CLASSIFIER — 加边界示例（P2）

**问题**：`confidence` 的 HIGH/LOW 判定靠纯文字描述，LLM 判定波动大。

**方案对比**：

| 方案 | 描述 | 优点 | 缺点 |
|---|---|---|---|
| A. 数值阈值 | "≥ 80% = HIGH" | 看似客观 | LLM 不擅长数值自评，实际效果差 |
| B. 加边界示例 | 补充 1-2 个模糊边界案例 | 示例比数值更有效 | 增加约 40 token |
| C. 不改 | 维持现状 | 零风险 | 判定波动持续 |

**选择方案 B，理由**：
- 业界经验：LLM 对数值置信度的自评极不可靠（同一输入不同次调用波动 ±30%）
- few-shot 示例对分类边界判定的效果远优于数值阈值
- 当前已有 4 个示例，补充 1-2 个边界案例即可

**Tradeoff**：不选 A 是因为数值阈值会让 LLM 陷入"我该给 75% 还是 85%"的内耗，反而降低一致性。

**改动**：在现有示例后补充边界案例：
```java
// PromptConstants.java INTENT_CLASSIFIER（在现有示例后追加）
// 追加到参考示例部分：
// - "这个方案有什么问题吗" → {"intent":"DISCUSS","topicTitle":"方案问题分析","confidence":"LOW"}
// - "我最近在学 Go，感觉挺有意思的" → {"intent":"CHAT","topicTitle":"","confidence":"LOW"}
```

**测试影响**：MessageRouterTest 用 mock LLM 返回固定 JSON，不依赖提示词内容，不受影响。

1. `mvn compile -pl dingRing-common` — 确认编译通过

4. 重启应用，发起一轮讨论，观察日志：
   - Agent 发言长度是否降到 100-200 字
